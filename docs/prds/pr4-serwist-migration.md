## 1. Context

### 1.1 Why migrate

The frontend ships a PWA today via `next-pwa@5.6.0`. That package is unmaintained
(no commits in over a year, no React 19 / Next 16 testing matrix), it peers on
React 18, and the Next 14→16 stack bump (PR1) already produced a peer-dep warning
on install. Continuing on `next-pwa` is an unbounded liability: the next Next
patch, the React Compiler opt-in, or a Workbox CVE could each force an
unplanned migration on a hot day.

`@serwist/next` is the maintainer-blessed successor — same Workbox primitives
underneath (precaching via `__SW_MANIFEST` injection, the same strategy classes
in runtime caching), but a TS-first API, an actively-maintained npm channel,
and first-class support for Next 16's app router. The official
`examples/next-basic` in `serwist/serwist` already targets `next@16.2.4` +
`react@19.2.5` (see
<https://github.com/serwist/serwist/tree/main/examples/next-basic>), which is
exactly the stack PR1 landed us on.

### 1.2 Current `next-pwa` integration points

| Surface | Location | Notes |
|---|---|---|
| Config wrapper | `frontend/next.config.mjs:1-25` | `withPWAInit({ dest: "public", disable: process.env.NODE_ENV === "development", register: true, skipWaiting: true })` wraps the export. |
| Manifest reference | `frontend/app/layout.tsx:8` | `manifest: "/manifest.json"` on the root `Metadata`. The file is hand-authored. |

## 2. Goals / Non-goals

### Goals

- **G1 — Drop-in replacement.** Same observable PWA behaviour after merge:
  installable, manifest-referenced from `app/layout.tsx`, SW registered on first
  load, skip-waiting on update.
- **G2 — Same precache surface + runtime cache parity.** Build artifacts
  (the Next chunks under `_next/static/...`) precached via `self.__SW_MANIFEST`;
  fonts / images / static JS / CSS runtime-cached the same way `next-pwa@5.6`'s
  default `cache.js` did. See §3.3 for the parity table.
- **G3 — Dev-disabled posture preserved.** `disable: process.env.NODE_ENV === "development"`
  carries over verbatim — `pnpm dev` produces no SW; `pnpm build` + `pnpm start`
  does.
- **G4 — No regression in the verification gates.** `pnpm install`, `pnpm lint`,
  `pnpm tsc --noEmit`, `pnpm test`, `pnpm build`, `pnpm exec playwright test`
  all stay green. Backend pytest unaffected (no backend changes).
- **G5 — Upgrade path documented.** First-visit users on the new build will get
  a one-frame swap (old SW → new SW activates after one navigation, courtesy of
  `skipWaiting: true`). Documented in §5.

### Non-goals (explicit; deferred)

- **Offline trip reading** — the trip-stream surface (`/api/trips/{id}/stream`)
  remains network-only. The user explicitly locked this scope.
- **App-shell-only mode** — no precaching of route HTML beyond what serwist
  emits automatically.
- **Dev-mode SW with debug scope** — dev stays SW-less.
- **Push notifications / background sync / periodic sync.**
- **Manifest generation** — `public/manifest.json` stays hand-authored. No
  switch to `next-manifest` or `@vite-pwa/assets-generator`.
- **Workbox version bump beyond what serwist ships.**

### 3.2 Config — `frontend/next.config.mjs`

Replace the `next-pwa` wrapper with the `@serwist/next` wrapper. The resulting
file:

```js
// @ts-check
import withSerwistInit from "@serwist/next";

const withSerwist = withSerwistInit({
  swSrc: "app/sw.ts",
  swDest: "public/sw.js",
  disable: process.env.NODE_ENV === "development",
  cacheOnNavigation: true,
  reloadOnOnline: true,
});

/** @type {import('next').NextConfig} */
const nextConfig = {
  reactStrictMode: true,
  typedRoutes: true,
  async rewrites() {
    return [
      {
        source: "/api/backend/:path*",
        destination: `${process.env.NEXT_PUBLIC_API_URL || "http://localhost:8000"}/api/:path*`,
      },
    ];
  },
};

export default withSerwist(nextConfig);
```

Key option mapping vs. the old `next-pwa` config:

| `next-pwa@5.6` option | Serwist equivalent | Notes |
|---|---|---|
| `dest: "public"` | `swDest: "public/sw.js"` | Serwist takes the full output path. |
| `disable: NODE_ENV === "development"` | `disable: NODE_ENV === "development"` | Identical semantics. |
| `register: true` | (n/a — default behaviour) | Serwist auto-injects the SW registration script in production. |
| `skipWaiting: true` | Set inside `app/sw.ts` (see §3.4) | Serwist exposes this on the `Serwist` constructor, not the wrapper. |
| (n/a — implicit precache) | `swSrc: "app/sw.ts"` | The TS entry point compiled into `public/sw.js`. |

`cacheOnNavigation: true` and `reloadOnOnline: true` are serwist defaults in the
`next-basic` example and align with `next-pwa`'s implicit behaviour (cache
navigations, attempt a reload when the user comes back online). No
`additionalPrecacheEntries` — we have no offline fallback page (deferred to
follow-up; see §8).

Canonical reference: serwist's official Next.js example at
<https://github.com/serwist/serwist/tree/main/examples/next-basic>
(`next.config.mjs`, `app/sw.ts`, `tsconfig.json`). The serwist docs site is
<https://serwist.pages.dev/docs/next/getting-started> — the example repo is the
ground truth; cite both.

### 3.3 SW source file — `frontend/app/sw.ts` (new)

Create a single TS file that mirrors the `examples/next-basic/app/sw.ts`
template, minus the `~offline` fallback (we don't ship one):

```ts
import { defaultCache } from "@serwist/next/worker";
import type { PrecacheEntry, SerwistGlobalConfig } from "serwist";
import { Serwist } from "serwist";

declare global {
  interface WorkerGlobalScope extends SerwistGlobalConfig {
    // Injected by @serwist/next at build time. Holds the precache manifest of
    // built artifacts (the Next chunks under _next/static/...). Matches
    // next-pwa's implicit precache behaviour.
    __SW_MANIFEST: (PrecacheEntry | string)[] | undefined;
  }
}

declare const self: ServiceWorkerGlobalScope;

const serwist = new Serwist({
  precacheEntries: self.__SW_MANIFEST,
  // Mirrors next-pwa's `skipWaiting: true` so users don't get stuck on the
  // old SW for an extra navigation after deploy.
  skipWaiting: true,
  clientsClaim: true,
  navigationPreload: true,
  // `defaultCache` is the @serwist/next preset closest to next-pwa@5.6's
  // cache.js defaults. See parity table below — we accept the small
  // differences (explicit RSC rule added by serwist) as net-positive.
  runtimeCaching: defaultCache,
});

serwist.addEventListeners();
```

#### Runtime cache parity vs. `next-pwa@5.6` `cache.js`

`next-pwa@5.6`'s default runtime cache (from
<https://github.com/shadowwalker/next-pwa/blob/master/cache.js>) and serwist's
`defaultCache` (from `@serwist/next/worker`) cover the same surfaces — fonts,
images, audio/video with range requests, static JS/CSS, `/_next/data/*.json`,
same-origin and cross-origin fall-throughs. The notable differences:

| Surface | next-pwa@5.6 | @serwist/next defaultCache | Verdict |
|---|---|---|---|
| Google fonts CDN (`fonts.gstatic.com`, `fonts.googleapis.com`) | CacheFirst / SWR | Same | Parity. |
| Static fonts (`.woff2` etc.) | StaleWhileRevalidate | Same | Parity. |
| Images (`.png`, `.jpg`, `.webp`, …) | StaleWhileRevalidate | Same | Parity. |
| `/_next/image` | StaleWhileRevalidate | Same | Parity. |
| Audio/video (`.mp3`, `.mp4`, …) with `rangeRequests` | CacheFirst | Same | Parity. We ship no media today, but the rule is harmless. |
| Static JS / CSS | StaleWhileRevalidate | Same | Parity. |
| `/_next/data/*.json` | StaleWhileRevalidate | Same | Parity. |
| Same-origin `/api/*` (excluding `/api/auth/*`) | NetworkFirst, 10s timeout | NetworkFirst, 10s timeout | Parity — but see §3.5 for the SSE carve-out we add on top. |
| Same-origin non-`/api/*` | NetworkFirst, 10s timeout | NetworkFirst, 10s timeout | Parity. |
| Cross-origin | NetworkFirst, 10s timeout | NetworkFirst, 10s timeout | Parity. |
| RSC requests (`?_rsc=…`) | No dedicated rule (falls through to "others" NetworkFirst) | **Explicit `NetworkFirst` rule** | Net-positive — serwist's explicit rule yields the same NetworkFirst semantics with a dedicated cache name, slightly better cache hygiene. Acceptable under minimum-change scope (still NetworkFirst). |

**Conclusion:** `defaultCache` is the correct match. We do not need to author a
custom `runtimeCaching` array. The single difference (explicit RSC entry) does
not change the observable strategy class on any request; it only changes the
cache name a response lands in.

### 3.4 SSE + auth carve-outs — `/api/trips/{id}/stream`

The trip stream endpoint must remain `NetworkOnly` (no SW interception, no
buffering, no timeout). Two reasons it is already safe:

1. **Same-origin `/api/*` is NetworkFirst with a 10s timeout** in both
   `next-pwa@5.6` and `@serwist/next` `defaultCache`. SSE connections never
   complete within 10s (they are intended to stay open), so a NetworkFirst
   handler would race the timeout against the stream and fall back to cache —
   except there is no cached entry, so the request would re-issue. In practice,
   Workbox detects the `text/event-stream` content type and skips runtime
   caching for it, but we should not rely on implicit behaviour.
2. **The SSE handler uses `fetch` with `EventSource`-style streaming in PR B's
   `useTripStream`** (see `frontend/lib/api/trips.ts` — added in PR B). SW
   interception of a streaming response would coerce it to a buffered response
   in some browsers.

**Mitigation** — explicit `NetworkOnly` rule for `/api/*` prepended to
`defaultCache` in `app/sw.ts`. The cleanest minimum-change approach:

```ts
import { NetworkOnly, Strategy } from "serwist";
// …inside the Serwist constructor:
runtimeCaching: [
  {
    // Bypass SW for all backend API calls — SSE streams must reach the
    // network untouched, and the JSON trip-create response should not be
    // cached either (the cycle is one-shot).
    matcher: ({ url, sameOrigin }) =>
      sameOrigin && (url.pathname.startsWith("/api/") || url.pathname.startsWith("/api/backend/")),
    handler: new NetworkOnly(),
    method: "GET",
  },
  ...defaultCache,
],
```

Match both `/api/*` (direct backend routes) and `/api/backend/*` (the rewrite
target). Method `GET` only — POSTs are NetworkOnly by default in Workbox.
Insert **before** `...defaultCache` so the rule wins matcher precedence.

This is a one-rule addition, not scope expansion — it's the documented
mitigation for the risk in §7-R2.

## 5. Rollout / migration safety

### 5.1 SW lifecycle on first user visit post-deploy

1. User on `feat/main`-deployed build has the **old** `next-pwa` SW
   registered at `/sw.js`.
2. After PR4 merges + deploys, the user's next visit:
   - Browser fetches the page HTML → finds the SW registration script.
   - Browser fetches `/sw.js` → byte-different from the cached registration.
   - Browser installs the new SW in parallel; the old SW continues to handle
     in-flight requests for this navigation.
   - New SW reaches the `activate` event; because `skipWaiting: true` (same as
     before), it takes over immediately without requiring the user to close
     all tabs first.
   - `clientsClaim: true` means already-open tabs are claimed by the new SW
     without a refresh.
3. **User-observable impact:** at most one extra round-trip during the first
   post-deploy visit while the new SW installs in the background. No visible
   reload, no broken page, no offline gap.

This is identical to the lifecycle `next-pwa@5.6` produced with the same flags.
The `skipWaiting` + `clientsClaim` combo is the documented "deploy and forget"
posture; we keep it.

### 5.2 If something goes wrong

- **Bad SW shipped** (e.g. it caches a broken asset): users can DevTools →
  Application → Service Workers → Unregister, or we ship a corrective deploy.
  Because `skipWaiting: true`, the corrective deploy is picked up on the next
  visit.
- **Manifest dropped** (would break installability): caught by acceptance
  criterion that `/manifest.json` returns 200 + valid JSON under `pnpm start`.

### 5.3 Rollback

Single-PR revert: `git revert <merge-sha>` on `main`. Restores
`next-pwa@5.6.0` and the old `next.config.mjs`. `app/sw.ts` is deleted by the
revert. Users on the new SW will see the old SW take over on next visit (same
lifecycle in reverse, same `skipWaiting`-driven swap).

No DB, no API contract, no env var, no infra change. Revert is safe.

## 7. Risks & mitigations

| ID | Risk | Likelihood | Mitigation |
|---|---|---|---|
| **R1** | `defaultCache` differs subtly from `next-pwa@5.6` `cache.js` → cache hit/miss ratio shifts post-deploy. | **Low.** | Parity table in §3.3 confirms strategy classes match on every surface; only cache *names* differ. Document in `app/sw.ts` comments. If a perf regression surfaces, the cache names give us a clean lever to author an explicit `runtimeCaching` array — not blocking this PR. |
| **R2** | SW intercepts `/api/trips/{id}/stream` SSE → blocks live event stream → `trip-flow.spec.ts` fails. | **Medium** without mitigation; **Low** with. | Prepend explicit `NetworkOnly` rule for `/api/*` and `/api/backend/*` in `app/sw.ts` (see §3.5). Verified by A8 (Playwright e2e). |
| **R3** | `pnpm-lock.yaml` conflicts on multi-developer env (Workbox 5 → 7 transitive churn is large). | **Certain (size); Low (correctness).** | Regenerate the lockfile cleanly via `pnpm install` after `pnpm remove next-pwa && pnpm add -E @serwist/next@9.5.11 serwist@9.5.11`. Do not hand-edit. Reviewer skims the top-level deps; the transitive churn is expected. |
| **R4** | The new SW caches a stale chunk → user sees blank screen after deploy. | **Very low.** | `skipWaiting: true` + `clientsClaim: true` + serwist's revisioned precache manifest mean stale chunks are invalidated by hash, not by SW lifecycle. Same mechanism `next-pwa` used. |
| **R5** | Build emits SW but `pnpm start` doesn't register it. | **Low.** | Serwist injects the registration script automatically in production builds; A6 verifies in DevTools. If it fails, check that `disable` didn't accidentally evaluate truthy. |
| **R6** | TypeScript fails on `ServiceWorkerGlobalScope` despite `webworker` lib. | **Low.** | The `@serwist/next/typings` package re-declares the relevant globals. Combined with `lib: ["dom", …, "webworker"]` this matches the `next-basic` example's `tsconfig.json` exactly. |
| **R7** | The unused `frontend/public/workbox-e9849328.js` from the old build hangs around in dev checkouts (it's gitignored but already on disk). | **Cosmetic only.** | Optional: Code Agent can `rm public/sw.js public/workbox-*.js` before the first `pnpm build` to keep the working tree clean. Not required — they'll be overwritten/replaced on build. |

## 8. Out of scope (followups)

Deferred per user's locked scope:

- **Offline trip reading.** Would need a custom `fallbacks` entry (an
  `~offline` page like the serwist example ships) plus an explicit cache rule
  for `/api/trips/:id` GETs. Not in this PR.
- **App-shell-only caching mode.** Would need `additionalPrecacheEntries` with
  the shell HTML pinned. Not in this PR.
- **Dev-mode SW with debug scope.** Would flip `disable` to `false` in dev and
  needs a separate `register: false` + manual registration story to avoid
  HMR conflicts. Not in this PR.
- **Push notifications.** Would need server-side Web Push keys + a
  `notificationclick` handler in `app/sw.ts`. Not in this PR.
- **Background sync.** Would need a sync queue for the trip-create POST when
  offline. Out of scope until offline trip reading lands.
- **Serwist v10 upgrade.** Currently in preview (`10.0.0-preview.14`).
  Re-evaluate when it reaches `latest`.
